# Zapara — контракт визуальной реализации

Дата: 2026-09-08. Основание — существующий Desktop и утверждённые локальные планы.
Это документация, не новый стиль, не реализация экранов и не свидетельство пройденного UI QA.

Поправка 2026-09-22: браузерный клиент — React в `web/`, его отдаёт сервер по `/app/`.
Фразы этого файла про будущий браузерный Razor описывают прежний замысел и админку.
Админка остаётся Razor. Таблицы цветов Desktop ниже — запись Windows и не переписываются этой поправкой.
Текущая картина продукта — `docs/STATUS.md`.

Решение 2026-09-22: единый стиль новых поверхностей берётся из Android, не из отдельной палитры сайта.
Источник — `android/app/src/main/java/ru/bgtu_voenmeh/zapara/ui/theme/Tokens.kt`, `Type.kt` и `LessonTypeStyle.kt`.
Сайт (`web/src/styles.css`) и токены админки (`src/Zapara.Server/wwwroot/css/admin.css`) используют эти значения.
Тем же решением 2026-09-22 телефон, сайт и Windows — один продукт: этот канон, тот же функционал и одна связь аккаунта. Таблицы ниже остаются записью текущего рабочего стола, пока Windows не сведён к канону. Отдельный стиль Windows больше не цель.
«Источник» ниже означает прочитанный код; «цель» — требование последующей реализации.

## 1. Характер, границы и источники

Сохраняем принятый монохром Inter: спокойные поверхности, тонкие границы,
инвертированные основные кнопки, штриховые иконки, цвет только по смыслу.
Фраза «Windows не перестраиваем» — снимок контракта 2026-09-08. С 2026-09-22 новые экраны Windows собираются из канона Android, как сайт и телефон. Android адаптирует этот рисунок к телефону; админка — к браузеру.
Публичное имя — «Расписание военмех». Zapara — внутреннее имя. Неофициальное приложение только для БГТУ «Военмех».
Ни приложение, ни роли сообщества не подразумевают одобрения университетом.
Цель всех трёх UI — русский язык. Английский UI и переключатель Windows ещё существуют;
их удаление — отдельная работа без изменения пользовательских данных и постороннего restyle.
Сценарии: студент без сети читает расписание/карты; участник работает со своим профилем;
персонал сообщества и администратор выполняют только разрешённые им действия.

T: `Radius.Card=12`, `Control=8`, `Chip=6`, `Pill=999`, `Dialog=14`, `Icon=9`, `Toast=10`.

### Android — координаты маршрута и стрелки, уточнение 2026-09-13 (задача 7)

Основание: утверждённые спецификация и задача 7 плана Android UI/maps от 2026-09-12.
`RouteGeometry` — чистая геометрия одного `RouteSegment`, не подключение нового UI.
Нормализованные координаты графа finite и в диапазоне 0..1 включительно преобразуются
в пиксели исходного JPEG строго как `x * width`, `y * height`. `RasterSegment.points`,
его bounds и default шага стрелок `64f` имеют растровые единицы, не dp и не layout pixels.
`legIndex` и `FloorKey` сохраняются; отдельные сегменты никогда не соединяются,
остаток расстояния стрелок между ними не переносится. Лестницы не становятся
плоскими линиями; локальный BuildingLink берётся только из сегмента адаптера Task 6.
Геометрия не определяет отсутствующую сторону перехода по `MissingMap`: при явно
переданном размере растра один этот флаг не стирает валидные точки.

Невалидная точка отвергает весь штрих, без clamp, фильтрации с мостом через разрыв
или выдуманной линии. Пустые/помеченные невалидными сегменты дают пустые points/arrows
и bounds=null. Одна точка сохраняет вырожденные bounds, но не стрелку; нулевая длина
также не даёт стрелок. `bounds` и `arrows` допускают отрицательные пиксельные смещения
layout; при неfinite входе возвращают null/пустой список, не NaN для Canvas.

`arrows(points, spacingPx)` требует конечный положительный spacing (иначе
IllegalArgumentException, в том числе для пустого входа). Образцы лежат на расстояниях
spacing, 2×spacing и далее вдоль штриха, включая точный конец, но без дополнительной
стрелки на коротком хвосте. Ненулевой путь короче spacing получает одну стрелку
в середине по длине пути, не в среднем арифметическом его концов. Нулевые рёбра
пропускаются; на точном углу касательная берётся с входящего ненулевого ребра,
после угла — со следующего. Реверс меняет начало отсчёта и направление касательных.
Длины вычисляются в Double; число образцов, не представимое размером List (Int),
отвергается пустым результатом до выделения памяти и обхода образцов.

Будущее подключение UI: один существующий ContentScale.Fit/letterbox переводит
координаты в layout pixels. `PathGeometry.onLayout` принимает нормализованные точки:
перед передачей растровой точки делить её x/y на ширину/высоту исходного JPEG,
не передавать туда растровые пиксели как нормализованные и не применять Fit повторно.
Для JPEG 1000×500 в layout 300×300 получаем drawn=300×150, origin=(0,75).
UI должен пересэмплировать той же `arrows` уже layout-точки с шагом **48dp**,
переведённым текущей density в layout pixels; это отдельный визуальный масштаб,
не замена растрового default 64f. Zoom/pan применяется ровно один раз общим
преобразованием карты и overlay, не повторно в геометрии стрелок.
Этот пункт задаёт контракт последующей интеграции: экран, MotionOff, fullscreen
и финальный UI QA задач 10–12 здесь не реализованы и не считаются пройденными.

### Android — основной план и шаги, Task10, 2026-09-13

`RouteStepBar`, `RouteStepsSheet`, `RouteMapOverlay` повторно используются обычной
картой и fullscreen. Карта получает остаток ограниченной высоты; chrome сверху
занимает не более 25%, шаги снизу не более 32% и имеют собственную прокрутку.

## 6. Движение и взаимодействие

M: `MotionSettings.Enabled = prefs.Animations && systemAllows`; `Duration(ms)` иначе 0.
Windows учитывает SPI_GETCLIENTAREAANIMATION; вне VM-контекста `Resolve` возвращает Off.
`App.SetMotion` снимает Motion.axaml; шаблонные части управляются самими контролами.
M: background/opacity/buttons 150ms, press transform 100ms, card 150ms,
NavIndicator 220ms, sidebar width 200ms; основная кривая `(0.2,0.8,0.2,1)`.
Исключение текущего XAML: hwdot 1→0.35 и mapglow 1→0.3, 1600ms alternate, SineEaseInOut.
Не утверждать, что весь Desktop уже transform-only: M анимирует также Height/Width и brushes.
A: переход раздела 180ms/8dp; индикатор 200ms; press scale 0.98 за 120ms; тема 220ms;
каскад первых 8 карточек 200ms/8dp, шаг 30ms, окно 400ms; skeleton цикл 1400ms;
ДЗ alpha 1→0.55→1 за 1600ms; карта 0.4→0.8 за 1200ms; zoom кнопками 200ms.
Pager/шторки — штатное движение с обязательным путём без анимации; кривая A `(0.2,0.8,0.2,1)`.
Android: настройка && ANIMATOR_DURATION_SCALE > 0; иначе нулевые длительности, остановка циклов/каскада.
Razor: учитывать prefers-reduced-motion; новая анимация не требуется, при добавлении — transform/opacity.
Уменьшение движения не удаляет статус, содержимое или обратную связь и не блокирует действие.

## 7. Поверхности и глубина

Desktop: смешанная стратегия — тональная ступень + граница, карточка в покое без тени (Y).
Точные T shadow-рецепты (порядок Avalonia: x y blur spread color):
`Shadow.Card`: `0 2 10 0 #66000000` Dark / `0 2 10 0 #14000000` Light;
`Shadow.Thumb`: `0 1 3 0 #40000000` / `0 1 3 0 #22000000`;
`Shadow.Dialog`: `0 16 48 0 #99000000` / `0 16 48 0 #33000000`;
`Shadow.None`: `0 0 0 0 #00000000` в обеих. Не придумывать дополнительные elevation.
Android A запрещает декоративные градиенты/blur/glow; исключения самого A — skeleton-блик и map-пульс.
Это не разрешение glassmorphism. Существующий C skeleton shine — служебный градиент, не бренд-фон.

## 8. Доступность, долг и будущая проверка

Цель WCAG 2.2 AA: обычный текст ≥4.5:1, крупный ≥3:1; значимые границы/индикаторы ≥3:1.
Проверять фактическую пару фон/текст с alpha; наличие токена не доказывает контраст.

для значимого текста выбирать пригодный существующий токен, не изобретать HEX и не прятать смысл.
Клавиатура: видимый focus, логичный Tab, Enter/Space, Escape/back, отсутствие ловушек и возврат из modal.
